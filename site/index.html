Baja Mineral Explorer — a reproducible geospatial data pipeline for mineral-exploration field planning

Ingests public geological, satellite, elevation, and mine-inventory data; validates and normalizes coordinates; ranks candidate targets; and produces GPS-ready field packages. This desk study organizes incomplete public evidence into explicit, field-testable hypotheses — it is not a discovery claim.

How the satellite data is gathered

A reproducible pipeline using documented data-access methods — no tile-server scraping of Google or Bing. Official APIs plus fully open data, all fetchable by script. Resolution figures below distinguish native sensor resolution from rendered display scale.

1 · Google & Bing — official routes only

Google data is used via Google Earth Engine (Sentinel-2, Landsat, ASTER, Sentinel-1) and the Photorealistic 3D Tiles API; Bing via the Bing Maps Imagery API (Aerial tiles to z18). Direct tile scraping violates ToS, is CAPTCHA-gated, and yields no spectral bands. The sub-meter viewing layer on this site is Esri World Imagery tiles (rendered display scale, not sensor resolution); the spectral viewing layer is the open Sentinel-2 2020 cloudless composite (EOX, CC BY-NC-SA 4.0 — a viewing product that prioritizes visual consistency, not analysis-ready reflectance); terrain uses SRTM elevation (~30 m native, resampled to a 10 m working grid — resampling adds no terrain detail) from USGS (public domain).

2 · Spectral & terrain screening per coordinate

For each coordinate the pipeline computes: an unvalidated RGB visual-screening heuristic (B/R ratio — a visual prioritization aid, not a clay/carbonate/iron mineral identifier), HSV surface classes (vegetation / soil / pale-tone / bright crust / shadow), and from the elevation working grid: slope, aspect, hillshade and drainage transects. Full-band mode (free Earthdata login) adds NDVI, ferric-iron, clay and carbonate indices at 30 m. Anything spectral requires validation with analysis-ready data and field observation.

3 · Geology cross-reference

Every site is cross-referenced against SGM Carta Geológico-Minera El Aguajito H11-B85, 1:50,000 (2009): Alisitos-terrane andesite/breccia (Kapa A-BvA), Cretaceous granodiorite–diorite intrusions, Late Cretaceous Rosario Fm, the La Turquesa Cu–Fe zona mineralizada, 14 documented workings, and the documented structure (NE–SW normals, N65–75°E veins, N–S relays, tabular brechas).

Target-scoring model (published)

Desk-screening ranks, not probabilities of mineralization. Since v3.0.0 the model is split: geological prospectivity and access/legal/environmental feasibility, shown side by side and never blended — a geologically interesting site can still be unsuitable. Deterministic — src/scores.py reproduces the committed ranks, and tests/test_scores.py enforces it in CI. Prospectivity weights: geology 30 · workings 10 (downweighted) · spectral 20 · structure 25 · exposure 15. Feasibility weights: access 35 · water/regulatory 35 · land constraints 30. Evidence tags: observed / derived / inferred / not-yet-assessed / requires-field-validation. v2 blended ranks (5.4/6.3/5.5) are frozen in the code for history.

Engineering decisions and tradeoffs

Why the system looks the way it does. Each point traces to code or docs in this repo.

Static field sheets, not a web app

Field areas have no connectivity, so the primary product is printable JPG sheets + CSV/GeoJSON for GPS apps (mode_spread). The website is a thin static mirror of the same artifacts — no backend to operate or secure.

Source selection: openness + license + scriptability

Every input must be fetchable by script under documented terms: EOX WMTS (CC BY-NC-SA 4.0), USGS S3 tiles (public domain), Esri tiles (research use), SGM PDFs. Google/Bing only via official APIs — see mode_tiles notes. Full table in DATA_PROVENANCE.md.

Coordinate normalization

WGS84 (EPSG:4326) in and out; Web-Mercator (EPSG:3857) only as an internal working grid for mosaics, UTM 11N for field bearings. Published records declare crs: EPSG:4326 and are validated by src/validate.py.

API failures and rate limits

Tile/elevation fetches use timeouts with graceful degradation (the demo shows “unavailable (offline?)” instead of failing). The public demo quota (5/visitor, browser-local) is honest rate-limit theater for a static host — real abuse protection would need a backend, which we deliberately do not have.

Caching and idempotency

DEM tiles are cached on disk and reused across runs; re-running scripts/build_data.py regenerates byte-comparable CSV/GeoJSON from the canonical record list. Stable v2 record IDs make repeated imports upsert-safe.

License preservation

Every record carries its own license field; map sheets print source credits in the footer; EOX non-commercial terms flow down to the site license (CC BY-NC-SA 4.0, see LICENSE).

Degradation when services are unavailable

No elevation API → distances still compute (pure haversine client-side); no imagery → CSV/GeoJSON packages still work offline. The low-bandwidth toggle drops Esri z18 layers entirely.

Version tracking

pipeline_version (currently 2.0.0) and created_at ride on every record; ID history v1→v2 is documented in schemas/datadictionary.md.

What would change at production scale

Server-side tile cache + COGs instead of hot-linking third-party WMTS; a real quota/backend for the runner; PostGIS only if spatial queries outgrow file-based GeoJSON. None of that is warranted for 36 pins and 14 workings — files are the database here.

Frequently asked questions

What is located at 30.048522, -115.236173?

The point sits on the NW slope of Cerro la Turquesa (740 m), San Quintín Municipio, Baja California, at ~617 m. This desk study identifies a km-scale pale surface ~1 km west, a straight NE–SW lineament ~1 km east (road vs fault scarp — to be checked in the field), and a turquoise-mining toponym at the site. It is the highest-ranked target under the current desk-screening model (prospectivity 7.2/10, feasibility 4.3/10) in the La Turquesa Cu–Fe epithermal corridor. No field survey, geochemistry, spectroscopy, or drilling has validated these targets.

How are the satellite maps for a coordinate produced?

A reproducible pipeline using documented data-access methods fetches, per coordinate: Sentinel-2 2020 cloudless viewing composite from EOX (rendered RGB, not analysis-ready reflectance), Esri World Imagery for viewing detail (rendered display scale), and SRTM elevation (~30 m native, 10 m working grid) for slope/aspect/hillshade. An unvalidated RGB visual-screening heuristic plus HSV surface classes and terrain statistics are computed per site, then cross-referenced with the SGM El Aguajito 1:50,000 (2009) geologic-mineral map. Anything spectral needs validation with analysis-ready data and field observation.

What is the La Turquesa corridor?

A documented low-sulfidation epithermal Cu–Fe (±Au) zona mineralizada mapped by SGM (1:50,000, 2009) in the Alisitos terrane, ~30.05–30.15° N, with 14 abandoned Cu–Fe workings (El Cardonal with documented turquoise; San Martín with chrysocolla, azurite and malachite; La Turquesa core; El Hormiguero; La Bonita; 5 Minas; El Sacrificio; Josefina; Santa Martha; Santa Lucía; La Víbora; El Moro), controlled by NE–SW normal faults and N65–75°E vein sets.

Is this investment or drilling advice?

No — it is an independent remote-sensing and geology desk study. Under Mexico's 2023 Ley Minera, new mining concessions are granted only by public tender, are prohibited in natural protected areas and water-stressed zones, and require prior consultation and social-impact studies. Water availability in this arid corridor is the main regulatory risk.

Is using Google or Bing imagery here legal?

Yes. Google/Bing data is accessed only through official channels (Google Earth Engine, Bing Maps Imagery API); the sub-meter base layer is Esri World Imagery; the analysis layers are fully open (Copernicus Sentinel-2, USGS SRTM). Tile-server scraping of Google or Bing is not used anywhere in the pipeline.

How do I run my own coordinate?

Use the public Demo section below — no login, up to 5 analyses per visitor. Enter lat/lon and the page places the point on satellite imagery, shows point elevation, computes distances and bearings to the 3 candidate targets, 36 pins and 14 documented workings, and produces a shareable link plus JSON/GeoJSON output and a downloadable field package. The 36-pin CSV/GeoJSON is also downloadable for GPS devices.
